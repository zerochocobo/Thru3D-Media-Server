## Thru3D 播放器兼容排查与 RVM 起播预滚（2026-10-11）

- 用户反馈自研 Thru3D（G:/code/VRPassthroughPlayer）播放虚拟MP4几秒即停。服务端核查：seek 路由策略默认 all，VMP4 不按 UA 分支，两次 206 正常应答；根因在播放器内置 mpv 的 stream_curl 把比 Content-Range 总长短的 206 当作 EOF。播放器侧已修（curl-max-request-size=32MiB 续拉、UA 改为 Thru3D/<版本> (Android; libmpv)），见播放器仓库当日交接。服务端无需为此修改。
- 旧版 Thru3D 发裸 "libmpv" UA，在 /passthrough_live 被 is_libmpv_screenshot_probe_ua 当作 Skybox 章节探测固定回 503，故旧版 live 不可用；新 UA 归类 libmpv/libmpv_like，不触发探测规则。PC 以新 UA + Range: 0-33554431 模拟：200 chunked、无 Accept-Ranges，20 秒 106MB 未截断。
- 观察未修：Thru3D 播 VMP4 时 mpv 约70秒22次回跳平均6.8MB重复下载（相同区间被请求两次），推测与虚拟MP4音视频交错距离有关；另有6次音频 underrun，播放位置紧贴编码前沿。
- 用户反馈 alpha 起播人物遮罩闪烁一阵后稳定。根因：每次起播/seek 调 reset_state() 清空 RVM 循环状态，冷状态前10～20帧遮罩不稳（代码日志原本即注明 warmup jitter）。真实8K VR片（sivr00434 part1，480s，40fps，参照=从477s以真实画面预热）测量 mean|alpha-参照|：冷启动 f0=0.0192/f5=0.0079/f10=0.0054；首帧预滚16次 f0=0.0071/f5=0.0051；32次 f0=0.0054。冷启动首帧相邻帧跳变0.0108，参照0.0031。
- 修复：config 新增 PT_RVM_START_PRIME_FRAMES（默认16，0关闭）。Matter.reset_state(prime_frames=N) 只记录待预滚次数；下一次实际推理前 _prime_rvm_state 在当前帧上额外推进 N 次（GPU _alpha_low_res_gpu_temporal 与 CPU _alpha_low_res 均接入，计数先清零防重入），日志 "RVM start prime"。仅 pynv_stream 帧流/live worker 与 stream.py 三个实时起播点传入配置值；缩略图、warmup、离线工具保持默认0不受影响。播放中途场景切换重置不预滚，避免在实时流上产生停顿。
- 验证：生产 GPU 路径（composite_green_profile）复测与探针一致（prime16 f0 0.0192→0.0071），16次预滚约0.16秒一次性开销；新增 RvmStartPrimeTests 3项，tests/test_matting_runtime_policy.py、test_matting_pool.py、test_predict_warmup_state.py 共36项通过。探针脚本在会话 scratchpad，未入库。需重启服务端生效，真机观感待用户复测；未提交。
