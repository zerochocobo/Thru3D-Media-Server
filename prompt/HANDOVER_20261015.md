## 美颜 CUDA 700 定位与修复

- 后续用户授权继续定位并修复，重点检查 RM→美颜。本轮未启动或重启用户正在使用的服务；GPU 验证全部在独立进程中执行。本机 RTX 5060 Ti，驱动 616.92，CuPy 14.0.1、ORT 1.25.1；用户日志的 GPU 为 RTX 5070 Ti。

### 已证实的缺陷

1. **美颜采样越界**：`offline/face_beauty_gpu.py::sample_rgb` 的双线性采样只限制了 x0/y0 的下界，没有限制 x1/y1 的下界。人脸对齐/landmark 的裁剪范围超出画面左侧或上方超过 1 像素时，x1/y1 仍为负数，直接读取图像之前的显存。带保护区的常量图实测：期望 100，旧核在 (-2.25,0)、(0,-2.25)、(-2.25,-2.25) 分别读出 175、175、194，证明读到了图像外的哨兵字节。修复为四个采样索引均限制到合法范围。
2. **VR 重投影同类越界**：`pipeline/vr_reproject.py::sample_eye` 也缺失上述下界。视角靠近半球边缘时，取景可超出当前眼的经度范围，读到另一眼或帧外内存。已对全部采样索引做眼内边界限制，覆盖普通及 supersample 内核。
3. **解码帧复制没有取得所有权**：`GpuNv12Frame.owned_copy` / `GpuP016Frame.owned_copy` 原用 `cp.ascontiguousarray`。解码面已连续时返回原地址；实测 3840×1920、4096×2048 的 Y/UV “复制”后均与解码器同址。PyNv ThreadedDecoder 的帧只在下次 get_batch_frames 前有效，保留 Python owner 不能阻止表面复用。已改为 `.copy(order="C")`，同时覆盖 8/10 bit，保持已有解码/拷贝完成同步。
4. **默认 stream 未传入 ORT**：`face_beauty_engine.onnx_providers` 原用 `if stream_ptr`，把有效的默认 stream 指针 0 当成未指定，造成 CuPy 与 ORT 并未按代码注释共享 stream。已改为 `is not None`，明确传入 0；只传公开的 `user_compute_stream` 选项。ORT 1.25.1 的 TensorRT EP 不接受显式 `has_user_compute_stream`，实测会触发 EP fallback，已移除该内部选项，避免修正 0 后意外退回 CUDA。非零 stream 同样使用受支持选项。

### CUDA 700 的因果验证与边界

- 在独立进程加载 b4f6dfa 的旧美颜 CUDA 核，构造画面外的仿射采样，再调用 ORT Identity 的 GPU IOBinding；旧核产生 CUDA 700，ORT stderr 同时报告 `cuda_execution_provider.cc:534 / cudaStreamSynchronize`，与用户日志的同步报错位置一致。改用修复后的核、相同输入正常返回常量 100。该测试使用极端负坐标来确定性访问非法显存，只证明旧核能造成同类错误，不代表已取得用户视频的真实裁剪坐标。
- RM→美颜的普通顺序切换在旧代码、本机测试片上也能成功，未发现或证明 RM 退出/接管逻辑本身必然存在释放竞态。已证明的越界、解码面所有权及 stream 问题会使 GPU 行为依赖画面和内存/任务时序；不能仅凭切换顺序将此次用户故障断言为 RM 的释放错误。
